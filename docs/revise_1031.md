# 桌面多物体抓取项目：鲁棒性修改思路

- 日期：2026-10-31
- 状态：待实施设计；本文不表示代码已修改或实机验收通过。
- 目标：提高机器人处理一个或多个不同类别桌面物体时，识别、抓取、放置、确认和完成任务的可靠性。
- 范围：本轮聚焦任务状态、快速视觉确认、失败记忆和尺寸计算；暂不调整托盘放置策略。

## 一、总体原则

本轮不做大规模架构重构。优先解决三件事：

1. 每个物体独立记录状态，不能只统计机械臂动作次数。
2. 利用“物体通常静止、机械臂每次动作后返位才重新观察”的现场条件，一次**有效观察**即可确认，不强制连续多帧投票。
3. 增加轻量失败记忆，避免重复尝试物理条件基本相同、已经明确失败的动作。

本方案适用于多个任意类别的物体，不限定为碗，也不限定为两个物体。碗只是当前测试对象。每个任务中的物体都应有独立记录和稳定的任务内编号。

## 二、第一优先级：逐物体状态和严格完成判定

### 2.1 每个物体有四种状态

| 状态 | 内部名称 | 通俗解释 | 进入条件 |
|---|---|---|---|
| 仍在桌面、尚未抓取 | `not_picked` | 物体还在桌面原位置，尚未完成搬运 | 初始识别到目标；或动作失败后确认物体仍在原处 |
| 动作已完成 | `motion_completed` | 机械臂已完成抓取、搬运、释放和返位，但还没有视觉证明放置成功 | 执行器报告动作链完成 |
| 等待视觉确认 | `pending_verification` | 等待相机确认物体确实进入目标区域 | 动作完成后建立待确认记录 |
| 已确认放置 | `verified` | 有效视觉证据确认物体进入托盘/目标区域，原桌面位置也已清空 | 当前有效观察通过关联和区域检查 |

状态流转：

```text
not_picked -> motion_completed -> pending_verification -> verified
```

补充规则：

- 抓取失败且物体仍在桌面原位置：保持/恢复 `not_picked`，不能增加成功数。
- 动作完成但视觉暂时看不清：保持 `pending_verification`，不能提前算成功。
- 物体从源位置消失，但目标区域也找不到对应物体：不能认定成功，应标记位置不明并有限重观察或报告异常。
- 如果执行器报告动作完成，但有效观察发现物体仍在源位置，应记录动作结果矛盾，先判断释放失败、物体滑落或关联错误，不能盲目重复抓取。

### 2.2 状态按物体管理，不能写死为双碗

建议每个任务维护物体记录列表，每条记录至少包含：

- `object_id`：本任务内稳定编号，不依赖 YOLO 每帧生成的临时 ID。
- `class_name`：物体类别，如碗、杯子、盒子等。
- `source_position`：桌面源位置。
- `target_position`：计划放置位置（如已分配）。
- `state`：四种状态之一。
- `last_observed_time`：最近一次有效观察时间。
- `release_id`：本任务内唯一释放记录编号（如已释放）。
- `verification_reason`：确认成功、未找到、匹配歧义、视野无效等。

每轮 YOLO 检测结果都要关联到已有物体记录。临时检测 ID 变化，不应自动创建一个新物体。关联可使用类别、位置、尺寸和图像框等信息；无法可靠关联时保留歧义，不强行认领。

计数从物体状态计算：

- `remaining_count`：仍在桌面、尚待处理的目标数。
- `pending_verification_count`：已执行搬运、等待确认的数量。
- `verified_count`：已经确认放置的数量。
- `motion_completed_count`：动作链完成的数量。

不能仅凭 `motion_completed_count` 判定任务成功。

### 2.3 完整任务成功条件

只有同时满足以下条件，才允许返回 `complete`：

1. 所有任务目标都已处理，没有仍在桌面的待处理目标。
2. 每次真实释放都有独立视觉确认。
3. `pending_verification_count == 0`。
4. `verified_count == motion_completed_count`。
5. 最终有效观察确认没有剩余待处理目标。
6. 机械臂已安全返回初始位。
7. 没有未解决的动作失败、身份歧义或物体位置不明。

如果动作都做完了，但一个物体没有得到可靠视觉确认，应返回 `partial` 或明确的未确认结果，不能报告完整成功。

开始时没有目标物体时，走独立 `no_targets` 路径：有效观察确认没有目标，动作数和确认数均为 0。

### 2.4 放置确认必须一对一

多个物体可能靠得很近。一个托盘检测结果不能同时确认两个释放记录。

- 先识别任务开始前就存在的托盘物体，不能拿它们作为本次新放置的证据。
- 再把当前帧检测与全部待确认释放共同匹配。
- 每个检测最多对应一个释放，每个释放最多被确认一次。
- 一个检测可能对应多个释放且无法区分时，标记 `ambiguous`，继续观察。
- `position_estimated=true` 的估计占位可以用于避让和规划，但不能作为视觉确认。
- 每个 `release_id` 只能确认一次，后续重复看到不能重复计数。

**实施建议：** 在现有 `ClearTableSession` 中集中维护状态和完成检查；在线 runner 与离线程序共用同一套规则，避免出现两套完成标准。

## 三、第二优先级：一次有效观察确认，快速处理视觉异常

### 3.1 为什么不强制连续两次或 5 次中 3 次

当前现场有三个重要条件：桌面物体通常静止；每次抓取动作结束后机械臂会返回初始位；返位后程序才重新获取图像、运行 YOLO 并规划下一轮。在没有机械臂接触、人员干预或其他外力的情况下，桌面物体通常不会自行移动。

因此，强制同一个物体连续两帧或多帧出现，可能只会增加等待时间，并让偶发坏帧拖住任务。

建议：**一次有效观察即可更新物体状态；无效观察不算成功，也不自动推翻之前已经成立的状态。** “一次有效观察”不等于“YOLO 返回一个框就算成功”。

### 3.2 一次观察满足什么条件才有效

抓放后的观察至少检查：

1. 图像及任务所需的深度/几何数据有效。
2. 托盘位置和区域投影有效，相关区域处于相机可观察范围。
3. 当前检测的类别、尺寸和位置与待确认物体基本匹配。
4. 物体确实位于托盘/目标区域内，而不是只靠近边缘。
5. 原桌面源位置本次可见，且没有再检测到对应物体。
6. 当前检测没有被任务开始前已有的托盘物体占用。
7. 当前检测与其他待确认释放没有匹配冲突。
8. 检测结果满足已有合理的几何和关联门限。

满足这些条件，一次观察就可以将对应物体从 `pending_verification` 改为 `verified`。一帧可以确认多个物体，但必须一对一匹配。

### 3.3 观察结果分三类处理

| 观察类别 | 例子 | 处理方式 |
|---|---|---|
| `valid` 有效 | 图像、托盘、源区域均有效，检测能可靠关联 | 按本帧证据更新对应物体状态；符合条件即可确认 |
| `invalid` 无效/暂不可判断 | 单帧检测失败、深度暂缺、投影越界、局部区域看不清 | 不增加确认；不清除此前已成立的状态；进行有限重观察 |
| `contradiction` 明确矛盾 | 已搬走物体又明确出现在原位置、托盘移动、物体明显掉落 | 只处理受影响物体，进入异常判断；不能当作普通坏帧忽略 |

规则：

- 一帧 `invalid` 不代表物体真的移动了。
- 一帧检测不到物体，不代表它从桌面或托盘消失。
- `invalid` 不得直接清空所有物体的确认状态。
- 只有明确反证才影响对应物体；一个物体观察失败，不能清空其他物体已经确认的状态。

### 3.4 推荐执行流程

```text
机械臂完成动作并返位
          |
          v
       获取图像
          |
          v
    检查观察是否有效
          |
    +-----+------+
    |            |
   有效          无效
    |            |
    v            v
逐物体一对一匹配   有限重观察
    |            |
    v            v
符合条件的物体确认 仍无效则有界退出
    |
    v
更新状态和剩余目标
    |
    v
重新规划下一轮
```

每次动作后用当前有效观察更新状态。若观察无效，只重新观察，不要因此重复执行机械臂动作。

最终任务结束也不必额外要求连续多帧空桌面：最后一帧有效观察确认没有剩余目标、所有释放均已确认、没有未决物体且机械臂已返位，就可以结束。

### 3.5 两种预算必须分开

**A. 观察/重观察预算 `observation_retry_budget`**

用于处理当前这一轮感知或决策无法继续的情况，例如图像获取失败、深度暂时不可用、托盘/源区域投影越界、检测结果不足以生成可靠规划。它限制当前观察/规划阶段最多再尝试多少次，不能无限重试。

**B. 放置确认等待预算 `verification_wait_budget`**

用于处理机械臂已经完成释放和返位，但当前视觉观察暂时无效、无法确认物体是否放好的情况。它只属于对应的待确认释放/物体，不能消耗下一只物体的规划或重观察机会。

建议实现为：

- 每次动作建立独立 `release_id` 和确认状态。
- 进入最终确认阶段时，为尚未确认的释放启动有限等待计时/次数预算。
- 中间仍有其他物体可处理时，保留待确认记录和估计占位，允许继续处理其他物体；不要让第一只物体的确认等待在第二只物体动作期间耗尽。
- 每次重新观察只消耗当前所处阶段对应的预算。
- 一个物体确认成功，只结束它自己的确认等待，不重置其他物体的失败记录。
- 确认预算耗尽仍无法看清时，返回 `partial / placement_unverified`，保留动作数、已确认数和未确认物体编号。
- 整个任务仍受总 deadline 和总观察轮数限制，防止局部预算叠加导致任务无限运行。

**快速方案的关键：** 正常情况下，一次有效观察就结束确认；预算只用于异常情况下的补救，不是正常流程中必须等待的多帧投票次数。

### 3.6 对当前代码的修改方向

- 在 `tools/place_rounds.py` 中，将观察结果明确分类为 `valid`、`invalid`、`contradiction`。
- 删除“某类 `observe_again` 就清零全部确认状态”的统一处理。
- 为每个释放记录确认状态和原因，不用一个全局确认计数代表所有物体。
- 在 runner 中分离普通观察/规划重试与放置确认等待。
- 将确认结果、无效原因、当前阶段和剩余预算写入结果 JSON。
- 在线 runner、离线流程使用相同确认规则。

不要简单把 `max_reobservations` 调大，也不要把连续确认次数改成 1 后就结束。真正要改的是：**一次有效观察即可确认；无效帧不抹掉有效状态；异常等待有独立上限。**

## 四、第三优先级：增加最小化失败记忆，避免重复尝试

### 4.1 失败记忆解决什么问题

例如：机器人尝试从某个角度接近物体，规划器明确判断这个接近姿态不可行。下一轮 Agent 只更换托盘放置位置，但物体位置、抓取方向和机器人起始状态都没变化。如果程序只比较完整候选 ID 或字符串，就可能把它当成新动作，再做一次同样的失败规划。

增加轻量“失败记忆”：记住本任务中哪些物理条件基本相同的动作已经明确失败，下一轮遇到相同条件时先跳过。

### 4.2 最小修改原则

不建设复杂数据库，不做跨任务长期学习。只在当前任务内保存少量失败记录，任务结束后随任务结果留档。

每条记录只保存判断重复动作需要的信息：

- 失败阶段：接近、下降、抬升、放置几何、放置路径等。
- 源物体位置。
- 实际接触点或抓取位置。
- 抓取方向/姿态。
- 机器人起始关节状态（如果该失败与起始状态有关）。
- 目标放置位置（仅当失败与放置位置有关）。
- 失败类别和原因。

### 4.3 不应该决定动作是否相同的信息

以下内容可以留在日志中诊断，但不应单独导致失败记忆失效：

- 拟合残差的极小浮点变化；
- 点数变化；
- 每帧变化的临时目标 ID；
- 精确槽位字符串；
- 仅用于显示或诊断的候选名称。

例如残差从 `0.001` 变成 `0.001000000001`，不能因此认为物理动作变了。

### 4.4 用物理容差判断是否为同一个失败动作

建议初始比较尺度如下，实施后再根据历史日志和回放调整：

| 比较内容 | 初始容差建议 | 说明 |
|---|---:|---|
| 源物体中心 | 5 mm | 小于该变化时，先视为近似同一源位置 |
| 接触点 | 2 mm | 判断是否基本是同一个接触位置 |
| 抓取方向 | 1° | 比较实际旋转角，不比较四元数字符串 |
| 目标放置位置 | 5 mm | 仅用于放置相关失败 |
| 机器人起始状态 | 沿用现有起始关节容差 | 起始状态明显变化时允许重新规划 |

四元数比较要考虑 `q` 与 `-q` 表示同一个旋转的情况，不能因符号相反误判为不同姿态。

### 4.5 不同失败阶段，记忆范围不同

| 失败阶段 | 应记住什么 | 哪些变化后允许重试 |
|---|---|---|
| 源接近/抓取姿态失败 | 相同源位置、接触点、抓取方向和相关起始状态 | 改变源位置、接触方向或有效起始状态 |
| 放置几何失败 | 相同目标位置和相关占用条件 | 更换放置位置或托盘占用发生有效变化 |
| 放置路径失败 | 相同放置目标、持物状态和相关场景 | 更换目标位置或场景确实改变 |
| 随机路径规划超时 | 记录短期失败，限制重复次数 | 允许有限重试，不永久认定不可达 |
| TF、通信、控制、夹爪等系统故障 | 记录故障并按安全策略停止/处理 | 故障恢复且状态重新验证后再决定 |

关键例子：

- 源抓取姿态失败，只更换托盘槽位：仍是同一个源抓取失败，应跳过重复源规划。
- 源抓取方向真正改变：允许重新尝试。
- 放置位置失败，换了一个新位置：允许重新规划放置。
- 服务超时或通信中断：不能永久记成“这个物体不可抓”。

### 4.6 代码修改范围

优先只改现有逻辑：

- `option_fingerprint()`：保留诊断用途，不再让无关字段决定物理动作是否相同。
- `register_plan_failure()`：记录失败阶段、物理条件和失败类别。
- `option_blocked()`：按物理容差和失败范围判断是否跳过。
- 候选规划返回结果：提供明确失败阶段和类别。

不必大改候选规划器，也不必引入数据库。失败记录数量很少，直接遍历并进行容差比较即可。

## 五、第四项暂缓：托盘放置策略本轮不改

本轮暂时不调整“靠边放”还是“居中放”、候选排序、托盘布局算法，也不改变现有用户指定的放置偏好。

原因：

- 当前最优先的问题是任务状态和确认结果是否可信。
- 放置策略涉及托盘尺寸、物体形状、间距、机械臂可达性和现场误差，应该在状态与日志可靠后再优化。
- 现在同时改变确认、失败缓存和放置策略，会让实机结果难以判断究竟是哪项修改带来的。

本轮只做尺寸概念统一，避免后续优化时重复增加余量。

### 5.1 用最简单的方式统一尺寸概念

建议只保留三个核心概念：

| 名称 | 通俗解释 | 用途 |
|---|---|---|
| `observed_radius` | 相机测得的保守物体半径，已经考虑当前测量的不确定度 | 表示当前观测到的物体实际占用范围 |
| `planned_radius` | 规划半径 = `observed_radius + placement_margin` | 放置规划时额外留出安全余量 |
| `association_tolerance` | 判断新检测是不是同一个物体/同一次放置的距离门限 | 用于视觉关联，不是物体尺寸，不参与半径相加 |

```text
planned_radius = observed_radius + placement_margin
```

`placement_margin` 是放置规划需要的额外安全余量，只在统一尺寸计算函数中加一次。网格生成、布局检查和占用更新都调用同一个函数，不能各自再加一遍。

视觉放后关联距离 `association_tolerance` 只用于判断“检测结果是否对应这只物体”，不能加到半径里，也不能当作机械臂放置误差补偿。

### 5.2 放置后的占用怎么处理

- 已经视觉确认的物体：使用最新有效观测得到的尺寸，再按统一规则计算规划占用。
- 尚未视觉确认的释放：使用保守估计占用，防止下一只物体规划时与它冲突。
- 从估计占用更新为实测占用时，要替换原占位，不能把两份尺寸叠加成两个物体。
- 不要因为一帧异常大/小的检测就永久扩大或缩小物体尺寸。

### 5.3 能否支持多个物体，而不是只有两个？

可以，而且应该从一开始就按多个物体设计。

上述三个尺寸概念对每个物体独立计算，不依赖任务中有几只碗。每个物体都有自己的 `observed_radius`、`planned_radius` 和关联门限。

需要区分：

- **本轮尺寸统一**：可以直接支持 1 个、2 个或更多物体。
- **本轮暂不改的托盘布局优化**：不承诺新增多物体全局最优排布算法。
- **未来若优化多物体布局**：应逐个物体检查；每放入一个物体就更新托盘占用，再为剩余物体重新规划，而不是写死“两只物体的位置配对”。

对于非圆形物体，不能强行把所有物体都当成碗来算半径。第一阶段沿用现有物体几何表示；若规划器只支持圆形近似，就使用能保守覆盖物体 footprint 的等效半径，并明确这是近似。后续需要时再扩展为矩形或多边形占用区域。

## 六、实施顺序与验收标准

| 顺序 | 工作包 | 主要修改 | 验收重点 |
|---|---|---|---|
| 1 | 逐物体状态与完成判定 | 四种状态、物体记录、一对一放置确认、严格 `complete` | 未确认物体不能算成功；多物体计数正确 |
| 2 | 快速视觉确认 | 一次有效观察确认；`invalid` 不清状态；`contradiction` 单独处理 | 一次有效帧可确认；坏帧不会清空已有状态 |
| 3 | 分离预算 | 普通重观察预算与每个释放的确认等待预算分开 | 第一只确认问题不消耗第二只的规划/重试预算 |
| 4 | 最小失败记忆 | 物理容差匹配、按失败阶段记录 | 微小浮点变化不绕过缓存；真实姿态变化允许重试 |
| 5 | 尺寸统一 | `observed_radius`、`planned_radius`、`association_tolerance` | 不重复加余量；多个物体各自维护尺寸 |

### 6.1 推荐优先检查的代码区域

- `tools/place_rounds.py`
  - 逐物体状态记录；
  - 释放记录和 `release_id`；
  - 一对一视觉关联；
  - 观察结果分类；
  - 统一完成条件；
  - 失败记忆的注册与拦截。
- `tools/test_live_place_pipeline.py`
  - 分离普通重观察和确认等待预算；
  - `table_complete` 必须再次核对本地完成条件；
  - 将每个物体的状态和未决原因写入任务结果。
- `src/yolo_vision/yolo_vision/placement_grid.py`
  - 本轮只核对半径和余量的使用，不改变选点排序。
- `tools/table_round_io.py`
  - 如有必要，输出物体状态、确认原因和尺寸诊断；Agent 不能直接决定本地确认结果。
- 对应测试至少覆盖 `tools/test_table_memory.py`、`tools/test_clear_table_runner.py`、`tools/test_visual_clear_table.py`、`tools/test_table_agent_protocol.py`，以及失败候选相关测试。

### 6.2 必须增加的离线测试

**逐物体状态与完成判定**

1. 初始识别到多个物体，全部为 `not_picked`。
2. 只完成一个物体动作时，其他物体仍保持 `not_picked`。
3. 动作完成但没有视觉证据时，物体保持 `pending_verification`，任务不能 `complete`。
4. 一个有效观察确认一个物体后，只增加一次 `verified_count`。
5. 一个检测不能确认两个释放。
6. 托盘原有物体不能被当成本次新放置证据。
7. 一个物体仍在桌面时，不能因为其他物体已确认就报告任务完成。
8. 物体从源位置消失但目标区域找不到时，不能误判成功。

**快速确认与预算**

1. 一次完整有效观察即可确认，不要求连续第二帧。
2. `valid -> invalid -> valid`：无效帧不清除之前已经确认的物体状态。
3. 连续 `invalid`：确认等待在预算耗尽后明确退出。
4. 明确 `contradiction`：只影响相关物体，不把它当成普通坏帧。
5. 第一只物体等待确认期间，第二只物体的规划预算不被消耗。
6. 一只物体确认成功，不重置另一只物体的等待状态。
7. 最终仍有未确认释放时，必须返回 `partial`，不能 `complete`。

**失败记忆**

1. 拟合残差微小变化、点数变化、临时 ID 变化，不应让同一失败动作重新尝试。
2. 源抓取失败后只换托盘槽位，不应重复做同一个源接近规划。
3. 真正改变源位置或抓取方向后，允许重新尝试。
4. 放置位置失败后换新位置，允许重新规划放置。
5. 服务超时不能永久标记为几何不可达。
6. 四元数 `q` 和 `-q` 应视为同一旋转。

**尺寸计算**

1. `planned_radius` 只增加一次 `placement_margin`。
2. `association_tolerance` 不参与半径相加。
3. 估计占位被实测占位替换，不形成重复障碍。
4. 多个不同物体分别计算尺寸，不依赖物体总数。
5. 非圆物体使用保守几何近似时，记录采用的近似方式。

### 6.3 实机验证建议

先完成离线回归和历史故障回放，再进行少量实机测试。不要一开始就大批量改动多个模块。

建议先验证：

1. 单物体：从桌面抓起、放入托盘、返位、一次有效观察确认。
2. 多物体：连续处理多个物体，确认每个物体的状态和计数独立。
3. 视觉间歇异常：某轮出现无效观察，之后恢复有效观察，任务能继续且不会重复执行已完成动作。
4. 持续视觉异常：超过预算后明确返回未确认，不误报成功。
5. 抓取规划失败：相同条件不会无意义重复尝试；条件真实变化后可以再试。
6. 放置确认歧义：两个物体靠近时，一个检测不能重复确认两次。

实机验收时，每次任务保存任务 UUID、代码版本、有效配置、物体清单、每个物体状态变化、动作次数、确认次数、重观察原因、失败记忆命中、最终图像和人工介入情况。

## 七、本轮明确不做的事情

- 不修改托盘“靠边/居中”策略和候选排序。
- 不把任务逻辑限制为两只碗；也不新增仅适用于双碗的特殊判断。
- 不引入复杂长期物体跟踪数据库。
- 不做跨任务自动续做或通用自动恢复。
- 不重构整个夹爪驱动；夹爪协议/事务改造另行评估。
- 不通过单纯放宽所有阈值或无限增加超时来掩盖问题。
- 不把一次 YOLO 检测框直接等同于成功；必须先通过有效观察和一对一关联检查。

## 八、最终建议

本轮最值得投入的是：**逐物体状态 + 一次有效观察确认 + 独立确认预算 + 轻量失败记忆**。尺寸统一作为小范围配套修改，托盘选点策略暂时保持不变。

这样改动范围可控，而且直接对应项目最核心的目标：机器人不只是“执行过抓取动作”，而是能够知道每个物体现在在哪里、是否真的放好、还有什么没完成，以及遇到短暂视觉问题时应该继续观察还是停止报告异常。
